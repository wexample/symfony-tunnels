# Tunnels defined in the database

Step 11 of `extract-from-network.md`, set aside as a project of its own. **Depends on** the dynamic forms of `symfony-forms` (see its journal todo "Forms defined in the database"): write those first.

## Goal

Let an administrator compose a tunnel from rows rather than code — a questionnaire, an onboarding — each step showing a form built in the database. The legacy used it for the `recette-2022` acceptance questionnaire.

## What the engine already offers

Nothing in the engine needs to change. A DB-defined tunnel is one generic step repeated with the row id as an option (`tunnel_step_entity_id`), which gives one cursor per row, and one manager whose steps come from the rows' `previous` relation.

## To build here

- `Entity/Tunnel` (name) and `Entity/TunnelStep` (name, self-referencing `previous`, `allowCompletedSession`, nullable form from symfony-forms).
- `Service/Step/AbstractEntityTunnelStep`: reads its row from the cursor option, lists the children rows in `getAllowedNextSteps()`, overrides `getPathGroupIdentifier()` (name + options) so each row is its own stepper entry, `tunnelSessionRecreate()` honouring `allowCompletedSession`, and `buildLabel()` from the row.
- A `CustomTunnelManagerService` + `DefaultStep` + controller on `/tunnel/custom/{name}/{step?}`: the route needs the tunnel name as a route param, given by `buildRouteParams()`.
- The submission is kept per cursor (`submission-id` variable) and prefilled on return.
- Cursor hashes include the row id: renaming nothing breaks, reordering rows does reset the sessions walking them.
- Demo: a small questionnaire in `symfony-tunnels-demo`.
